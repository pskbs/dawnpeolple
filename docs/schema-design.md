# DB 설계안 (검토용 — 아직 적용 안 됨)

파일: `supabase/migrations/0001_init.sql`
상태: **초안. 실제 Supabase 프로젝트에는 아직 반영하지 않았어요.** 검토 후 말씀해주시면 적용할게요.

## 무엇이 들어있나요
1. **테이블 18개**: 요청서 6-1에 나온 것 그대로 만들었어요 (프로필, 글, 댓글, 좋아요, 벙개, 참석자, 신고, 차단, 제재, 관리자 로그 등).
2. **모든 테이블 RLS(행 단위 보안) 켬**: 기본은 "아무도 못 봄"이고, 아래처럼 필요한 경우에만 열었어요.
   - 내 정보는 나만, 관리자는 전체 조회 가능
   - 수다방 글/댓글은 "보임" 상태면 누구나 조회
   - **벙개 참석자 명단과 참석자 전용 댓글은 참석자 본인 + 그 벙개의 리더 + 관리자만** 볼 수 있어요. 참석 안 한 사람은 절대 명단을 못 봐요.
3. **"남은 자리" 계산은 별도 함수로 처리**: 미참석자가 몇 명 참석했는지 알 수 없게, "남은 자리 숫자"만 돌려주는 함수(`get_bungae_remaining_slots`)를 만들었어요. 참석자 목록 자체는 노출 안 돼요.
4. **동시에 여러 명이 신청해도 정원을 넘지 않도록** `join_bungae` 함수 안에서 행을 잠그고 확인 후 등록해요(이른바 "경합 처리").
5. **참석 취소는 모임 시작 3시간 전까지만** 가능하게 `leave_bungae` 함수에서 체크해요(시간은 나중에 설정으로 바꿀 수 있어요).
6. **닉네임 변경은 7일에 한 번만** 되도록 `change_nickname` 함수에서 막아요.

## 아직 안 만든 것 (다음 마이그레이션에서 추가 예정)
- 벙개 개설 한도(하루 2건, 동시 3건, 신고 3건 자동 비노출) 체크 로직 — `create_bungae` 함수는 다음 단계에서 작성할게요
- 온보딩 완료(프로필 최초 생성) RPC
- 회원탈퇴/토스 연결 해제 처리 함수(6-3)
- 신고 3건 누적 자동 처리, 관리자 제재 적용 로직

## 검토해 주실 포인트
- 테이블/컬럼 이름이나 값 범위(예: 벙개 인원 2~10명)가 요청서와 다른 부분이 있으면 말씀해 주세요.
- 이 설계로 괜찮으면 "적용해줘"라고 말씀해 주시면 Supabase 프로젝트에 반영할게요. (참고: 지금 가진 키는 anon key/service role key뿐이라, 실제 적용에는 Supabase 대시보드의 SQL Editor에 직접 붙여넣거나, Supabase CLI 로그인이 추가로 필요해요 — 적용 방법은 승인 주시면 그때 안내드릴게요.)
